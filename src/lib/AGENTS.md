## Payments & badges rules
- Feedback is scoped to an explicit root/alias/workspace binding; anonymous reads/submissions use narrow DB functions that enforce profile visibility and rating ranges. Featuring requires respondent consent; Studio mutations require active-scope developer access. Why: no cross-tenant or cross-namespace reviews, private response leaks or non-consensual testimonials.
- First-use tours store authenticated, per-area completion in profiles.display_prefs.firstUseTours; no browser storage or auto-auth is involved. Why: guidance follows the member across devices without changing login behavior.
- Root and alias profile saves share profile-image-url.ts for image validation, allowing only the exact first-party avatar fallback among relative URLs. Why: uploaded photos must persist without accepting arbitrary application paths.
- profile-surface.ts derives automatic card, border and text roles from the selected solid canvas; explicit user colors remain overrides. Why: frames and messages must not inherit an incompatible old preset.
- Tip pages never move money through ROUT: EPC/SEPA QR + text IBAN is the always-on default; optional creator-owned PSP keys (Stripe/Mollie) live only AES-GCM encrypted in `psp_credentials` (db/58, `crypto/secretbox.server.ts`, `PSP_ENCRYPTION_KEY`) and are decrypted only inside `startPspTip`. Why: zero platform liability and no plaintext third-party secrets.
- Tip settings/PSP access requires a verified account with a root handle, checked in every `tip-page.server.ts` entry point; the IBAN holder must match the verified legal (or approved business) name. Why: prevents fraud via free aliases.
- Custom badges (`custom_badges`/`user_custom_badges`, db/57 + heraldry fields db/86, rendered only via `components/profile/BadgeEmblem`) are admin-granted and additive to the identity mark; influencer/business badge types are coerced server-side unless approved, and privacy-shield profiles never return legal name/country from `readPublicProfile`. Why: privacy and exclusivity enforced at the boundary, not the UI.
- Live Presence providers (Spotify first) store sealed tokens in `user_presence_connections` (db/68) and are read publicly only via `/api/presence/now-playing`, which requires the member's `show_on_profile` opt-in. Why: tokens never leave the server and visitors see only opted-in track info.
- Email trust badges come only from `email-trust.ts`: provider/sovereign badges need a strict provider vouching for its own mailbox domain; custom domains need our DNS/TXT proof. Why: expired-domain takeovers must never look trusted.
- Snapchat (`snapchat.server.ts`, `user_snapchat` db/87) is a link-only Snap Kit flow: no token kept, no location, Bitmoji shown publicly only via the image proxy and opt-in flags. The hub and both add dialogs read the shared `my-snapchat` query; activation updates only `showCard`, never generic integration rows or mood. Why: Snap gives no e-mail for account creation, and visitor IPs must not reach Snap.
- Files live in Scaleway Object Storage via `src/lib/storage/s3.server.ts` (client bucket = member data under `users/<uid>/`, internal bucket = ROUT assets, admin-only); Neon stores only metadata. Why: keeps blobs out of the database; member data separate from platform assets.
- Page share images are drawn in code (`src/lib/page-og.server.ts`) from the single logo source `src/lib/brand/logo.ts`, one per page per locale at `/brand/og/<page>-<locale>.png`, cached in the internal bucket; never AI-generated, never rotated. Why: brand fidelity, cache stability.
- Rate limits are counted in Neon (`rate_limits`, db/64) via `hitRateLimit`, failing open on db errors. Why: limits must hold across instances.
- The "oidc" sign-in provider ("ROUT ID") falls back to our own OIDC issuer with first-party public PKCE client `rout_native_self` (db/78, owner_user_id null) when no OIDC_* env vars are set; partial OIDC_* config disables it. Why: sovereign login must work with zero external keys.
- Sensitive account changes (merge, setting/resetting a password, 2FA on passwordless accounts) require a 6-digit e-mail code from `security-code.server.ts` (`security_codes`, db/84). Why: a live session alone must not be enough for irreversible changes.
- Account merge moves every public row with `user_id`/`profile_id` (row by row, duplicates dropped) and re-homes Better Auth accounts via `user_metadata.neon_auth_id`; the unchosen card design is saved in `profile_design_templates`. Why: nothing may be lost or duplicated, and sign-ins must keep resolving to the kept account.
- Influencer/business verification hands out names through the `approved_handles` whitelist (db/45); users claim exactly one via `claimApprovedHandle`. Why: the admin approves names, never types them.
- Bluesky/Mastodon accounts without a provider-verified email are created or linked only after a hashed 6-digit email code (`fediverse-otp.server.ts`, db/46). Why: typed emails allow takeover.
- Birthdates live in the separate `user_birthdates` table (db/48), written only via `saveMyBirthdate`; verification returns `birthdate_required` until present. Why: keeps legal data out of mass-assignment paths.
- Uploaded user files are tracked in `user_assets` (db/80) with retention set server-side by `asset-retention.ts`; expired rows are purged by `/api/public/cron/cleanup-assets`. Why: storage never grows without an owner or an end date.
- Public Spotify reads go through the `user_music_status` cache (db/85, ~10 s freshness) and return the server `syncedAt`; the widget interpolates locally. Why: visitors must never fan out into Spotify rate limits.
- Hub connections live in `user_integrations` (db/73) with a per-row Pro/Social/Both audience; `verified` is set only server-side when the handle matches a sign-in identity. Why: typed handles must never look proven.
- Total reach is summed only from Connections Hub rows (`user_integrations`, db/74): open platforms auto-fetch, others use a per-integration manual count; never social_links or placeholders. Why: the number must reflect what the member actually connected.
- YouTube vault (`youtube.server.ts`, db/95) reuses the Google client keys in a separate OAuth flow (youtube.readonly, offline) and seals tokens on the `user_integrations` 'youtube' row; failed refresh sets `connection_status='disconnected'`, disconnect revokes and deletes the row, visitors read only the cached card via `/api/public/youtube/card`. Why: Better Auth sign-in stays untouched and tokens never leave the server.

- Guestbook (`guestbook.server.ts`, db/90): only signed-in verified, unblocked members post, owners pin/delete via `owner_id` checks, public reads return pinned notes of public profiles only. Why: verified network effect, no spam, privacy enforced server-side.
- Admin gifts share gift-issue-rules, activate atomically and resolve recipient email server-side; mail status comes from the central sender. Why: preserve checkout value and recipient privacy without false delivery claims.

- Creator payment keys: Stripe accepts only restricted keys (`checkStripeKey` in `tip-rules.ts`, enforced in `savePsp`), sealed with secretbox, decrypted only inside the payment handler. Why: a leaked full secret key would expose the creator's whole Stripe account.
- Live-status windows: `live-presence-rules.ts`, applied server-side. Why: no client trust.
- Open-web ownership: server-side bio-check only (`checkBioVerify`); `verified_via` 'sso'|'bio', handle change drops bio; user fetch hosts pass `isPublicHost`. Why: no client trust, no SSRF.
- Stamps: lock links before redeeming in one gateway transaction; enforce public profile visibility. Why: no cap overruns or private collections leaked.
- Profile sections use profile-section-blocks.ts and blocks; explicit hidden/scheduled sections suppress fallbacks. Why: no duplicate or resurrected content.
- Standalone profile QR saves update live settings and the private draft atomically, advancing draft revision; sharing uses the saved generator settings. Why: stale Studio publication must not overwrite the QR design.
- Profile QR save controls read the active generator's React context, not module-global state; saved-style hydration compares only that instance's edits. Why: immediate saves and multiple designer instances must not store a default or unrelated design.
- Showcase cards expose a narrow normalized presentation subset and share ShowcaseIdentity rendering; first-party avatar paths stay local and remote images use the allowlist proxy. Why: live examples match profile styling without exposing private settings or visitor IPs.
- AT ownership checks use exact member ROUT hosts and the shared deterministic bio parser; well-known fetches validate public DNS addresses and refuse redirects. Why: nested lookalikes and internal hosts must never establish ownership.
- Community stats are live counts; reviews show only when `approved` (db/65); empty sections hide. Approving a verification cancels that user's other open same-tier requests (`verification-dedupe.ts`). Why: no fake social proof or duplicate work.
- ALTCHA uses self-hosted single-use proofs; db/54 owns replay DDL, unavailable storage fails closed, invalid proofs are refused before auth. Why: least privilege without weaker bot protection.
- Personal-to-Workspace conversion (`workspace-conversion.server.ts`, db/103) runs only after both an e-mail code on the source account and acceptance by a verified owner, in one `sql.transaction`; converted logins are refused by `requireAuth` until the sunset scrubber deletes them. Why: no half-moved data and no company logins.
- Workspace conversion moves the Stripe customer id onto `workspaces` and clears it from the user in the same transaction; its mails are app-rendered intents (`workspace-owner-invite`, `workspace-member-onboarding`) with copy in `emails/design/workspace-copy.ts`. Why: no double billing, and no Brevo template is needed.
- Booking engine (`src/lib/booking-engine`, db/104): instants are UTC timestamptz only; synced calendars store only HMAC id/start/end/blocking via `adapters/zero-knowledge.ts`; visitors read pre-computed `availability_cache` bit(96) days; booking = one batch (advisory lock per host+UTC day, assert, insert) backed by the GiST EXCLUDE. Why: no PII, no N+1, no double booking.

- Outbound webhooks are signed only via `webhooks/signature.ts` (`X-Rout-Signature: t=..,v1=hmac`) and delivered from the `webhook_deliveries` queue by the deliver-webhooks cron with `nextRetryDelaySec` backoff; endpoint secrets are sealed. Why: receivers can verify origin and replay window, failures retry without blocking.
- Booking intake uses booking-engine/intake.ts for shared validation and sensitive-answer separation; external AI paths must never receive answers. Why: guest medical and dietary data stay private.
- Studio draft saves validate with `draft-json-schema.ts` (nested JSON, bounded) and fail as structured `SaveErrorInfo` from pure `save-errors.ts` via `draft-save.server.ts`; conflicts return the current revision so the editor rebases. Critical failures mail the admin via `email/error-reporter.server.ts`, max 1 auto mail per error type per 15 min. Why: a flat schema silently refused every nested pref, and bare 500s hid the cause.
- Short-link direct redirects are decided only by pure `short-link-trust.ts`. Incoming signed webhooks use `webhook-replay.ts` (300 s window). User-supplied outbound URLs go through `safe-fetch.server.ts` (`assertPublicHost`). Why: one tested rule each for redirects, replays and SSRF.
- YouTube live presence comes only from hub pushes (`/api/public/youtube/push`, signature per channel) with a 15-minute TTL in pure `youtube-presence.ts`. Why: no polling quota and no stale "live".
- Emailed action links (review, booking) only confirm on GET, change on POST; status mails send fire-and-forget. Why: scanners open links; mail failures never block actions.
- 2FA/passkeys: Better Auth `twoFactor` + `@better-auth/passkey`, tables in `neon_auth` (db/77). Why: no custom crypto.
- Hold back a migration via `migrate-gateway.ts --only=<files>`. Why: some wait on a deploy.
